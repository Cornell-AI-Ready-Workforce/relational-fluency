Lane 2 · the real thing

Run a live encounter

A real conversation on the real gateway, with a real microphone and a real webcam recording, through GET /test — the same entrance the lab already uses to walk the study. What makes it a demo is settled before the conversation starts, rather than sorted out afterwards: /test mints the run cohort=internal and writes that tag onto the participant record it mints with it, so this encounter's cohort is not re-derivable by anything that happens later, and every ?cohort=study export leaves it out. It is excluded from the analysis set; it is not hidden from the screens. See Where a demo shows up afterwards, below.

Two things worth saying out loud before you press it. On the model this deployment is configured for, the room will see no steering at all — the card below says exactly what that looks like, and it is the question you will be asked. And the one thing that can still carry a demo into the analysis set is a person: the tag lives in files, and a rating assignment handed an explicit list of session ids never consults a cohort.

  • The run is tagged cohort=internal. /api/runs, /api/encounters and /api/sessions all drop it from ?cohort=study, and the tag reaches the encounter's own manifest, so an offline tool reading the session directory sees it too.
  • The participant key says so in words. Whatever you type below is sent with a demo- prefix, so the key on the run reads test_demo-lab_… on every surface that prints one. The cohort is a field somebody has to think to filter on; the key is printed whether they thought of it or not.
  • The consent record says internal_test. There is no Qualtrics response behind a demo and there never will be, so the record points at the internal run id instead of inventing one. It never claims a survey consent, and the microphone still opens only once a consent record exists — that gate is the same one every participant passes.
  • The screen says DEMO for the whole encounter. The participant page runs inside the demo frame, with this band above it and the run id beside it, so nobody watching has to be told twice.

Steering

Where a demo shows up afterwards

Excluded, not hidden. A demo is a row in every unfiltered list — /api/encounters, /api/sessions, the researcher console's session picker, the evidence trace's session list — sitting beside the study's, newest first, which usually means at the top. What removes it is the cohort filter: ?cohort=study on /api/runs, /api/encounters and /api/sessions all leave it out, and that is the analysis set.

Where the mark is. The manifest, /api/runs, /api/encounters and /api/sessions all carry cohort: "internal". The researcher console prints [INTERNAL] at the head of the row. The evidence trace badges it INTERNAL where a study encounter reads STUDY.

Two more marks, and they belong to this page. A demo started from this page carries a participant key beginning test_demo- — the field above forces that prefix — and a consent record reading consent_source: "internal_test" with the internal run id as its reference, which is what the handoff to /v2 writes. An internal run started some other way — GET /test with a name of its own, which is how the internal encounter already on this tree was made — carries the cohort tag and neither of these two. Read cohort for the question "is this study data"; these two are for recognising a demo at a glance.

One field here does not mean cohort. /api/encounters also returns study: true or study: false, and that flag answers only whether the scenario is one of the eight v3 study scenarios. A demo runs those same scenarios — that is what makes it a demo of the study — so a demo encounter reports study: true. Read cohort. Never read study to tell a demo from a participant.

If you want a demo gone rather than merely excluded, delete its run file and its session directory. Nothing here does that for you, on purpose: this page starts things, and a page that also deletes recorded encounters is one misclick from deleting somebody's.
